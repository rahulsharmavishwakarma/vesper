# September 2026 RSI research for local dictation

Reviewed **18 September 2026**. Main window: **1–18 September 2026**. Paper dates below are first arXiv submissions, with the inspected version stated; project announcements and code releases can have different dates. This is a targeted primary-source survey, not an exhaustive bibliography. Late-August context is explicitly separated. Issue [#34](https://github.com/rahulsharmavishwakarma/transcribe/issues/34) owns implementation proposals and approvals.

The product requirement remains automatic, on-device improvement during ordinary use, with application-owned memory surviving model changes. The most applicable research changes memory, retrieval or bounded application policies while leaving weights frozen. None of the surveyed results establishes that this application's small local models can autonomously improve dictation quality. No external model API, dependency, training runner or live policy controller was introduced by this review.

## Recent papers and their usable ideas

The findings column records **paper evidence**; the last column is an **engineering hypothesis for this app**. Published tasks, models and scores are not local qualification.

| Source and date | What changes; evidence and limitation | Application idea to evaluate |
| --- | --- | --- |
| [MASkills](https://arxiv.org/html/2609.02094v1), **2 Sep, v1**; [submission record](https://arxiv.org/abs/2609.02094) | Evolves individually addressable skills through refinement, induction, consolidation and pruning, using skill-level credit and validation. Tests QA, conversational memory and agent tasks. Uses a larger optimizer model; this is not evidence for cheap laptop optimization. | Attribute benefit/harm to the specific memory used. Consolidate duplicates and reduce harmful rules rather than only growing vocabulary. |
| [MetaRSI / RSI2](https://arxiv.org/html/2609.06396v2), **6 Sep v1; 9 Sep v2**; [submission record](https://arxiv.org/abs/2609.06396) | Separates data, harness and model updates, with bounded writable components and protected evaluation/release machinery. Includes frozen-weight and training routes on coding/scientific tasks. | Keep vocabulary admission, context retrieval, update-policy changes and future acoustic training separate, each with attributable outcomes. |
| [SE-GoS](https://arxiv.org/html/2609.08228v1), **8 Sep, v1**; [submission record](https://arxiv.org/abs/2609.08228) | Changes retrieval graph relationships, weights and descriptions using execution traces, without changing skill bodies or model weights. Its repeated-update experiment improves initially, then regresses in round three. | Learn when an existing word is relevant separately from learning its spelling. Require multi-round negative cases before making context adaptation continuous. |
| [Generalized Agent Iteration](https://arxiv.org/html/2609.13406v1), **11 Sep, v1**; [submission record](https://arxiv.org/abs/2609.13406) | Formal framework distinguishing an editable improvement mechanism from ordinary iterative updates, and external evaluation from self-referential scoring. It is not an empirical dictation benchmark or implementation release. | Keep the learner from changing its own definition of success. Report memory adaptation and improvement of the update procedure separately. |
| [Dream-RSI](https://arxiv.org/html/2609.14858v1), **14 Sep, v1**; [submission record](https://arxiv.org/abs/2609.14858) | A fixed agent revises exploration-policy code against recorded discovery trees, then uses the selected policy for new discovery. Weights stay fixed. Experiments concern algorithms, mathematics and kernels, using Gemini agents. Replay exposes recorded continuations; it cannot invent unobserved outcomes. | Reuse independently supported correction episodes to compare bounded local policies before allowing a candidate to affect future dictation. |
| [ScienceBuddy](https://arxiv.org/html/2609.17523v1), **15 Sep, v1**; [submission record](https://arxiv.org/abs/2609.17523) | Turns researcher interaction and execution evidence into tasks/rubrics. An inner loop changes the harness with weights frozen; a separate outer loop trains the model. Includes paired development checks and separate validation. Uses a frontier auxiliary model for harness diagnosis. | Turn an actual corrected mistake into a reusable scoped regression case. Explore the inner-loop idea; the training loop remains outside current product scope. |
| [Self-Evolving Search Index](https://arxiv.org/html/2609.19656v1), **17 Sep, v1**, work in progress; [submission record](https://arxiv.org/abs/2609.19656) | Diagnoses retrieval failures, revises index keys and validates changes while preserving underlying documents. Generated queries broaden exploration. Evaluates retrieval and memory tasks with much larger optimizer/judge models than this app. | Preserve user-authored wording and provenance while improving lookup/context keys. Synthetic queries test a hypothesis; they do not establish what a user intended. |

Dream-RSI's incumbent-included selection guarantees no worse score **on that fixed replay history**, not on future interactions. Its discovery objective also differs from minimizing every user's correction burden. Our adaptation should retain independently labelled adverse cases and report all episodes, rather than importing its objective or treating replay success as a deployment guarantee. This is our application assessment of [§3](https://arxiv.org/html/2609.14858v1#S3).

### Z.ai inspiration: diagnose, replay and verify

Z.ai reports roughly **3× serving throughput over its initial baseline** while preparing GLM-5.3-Flash infrastructure. Its agent connected correctness checks, runtime traces, small benchmarks and whole-service tests; engineers retained responsibility for objectives and critical review. The authors explicitly say full RSI has not been reached. These are claims about their infrastructure, not evidence of faster or more accurate local dictation. See the [primary article](https://z.ai/blog/glm-built-its-inference-infrastructure).

**Independent upstream artifact checks:** [Flash Linear Attention PR #1180](https://github.com/fla-org/flash-linear-attention/pull/1180) merged on **27 August 2026**, before the post, at `81c015566edf4de0a6f95661c09f3de43949ec2b`. Its precision path is **opt-in**, with default behavior retained on supported NVIDIA hardware; unsupported hardware uses an explicit IEEE fallback. The PR adds multi-GPU regression cases and describes an accuracy change, not a performance improvement. In [DeepEP v1.2.1 source](https://github.com/deepseek-ai/DeepEP/blob/9af0e0d0e74f3577af1979c9b9e1ac2cad0104ee/csrc/deep_ep.cpp), `internode_dispatch` releases the Python GIL; the intra-node dispatch/combine paths lack that release. The intra-node receive-counter wait is conditional: cached operation and worst-case preallocation bypass it. These observations corroborate specific mechanisms, not agent authorship or production gains. Neither upstream implementation was executed here, and neither establishes a matching bottleneck in this Rust desktop application.

**Our application assessment:** distinguish improving the shipped software during development from adapting one user's application memory during use. Both need objective feedback, but only the latter belongs in the current automatic product loop. The following table maps the ideas to experiments; the failure-bank comparison now has results below, while richer live attribution and timing remain proposals:

| Question for this app | Existing foundation | Concrete experiment and boundary |
| --- | --- | --- |
| Did recognition, cleanup or an applied memory cause the correction? | Retained sessions separate raw, cleaned and personalized text; correction evidence identifies applied entries. Collection-off behavior retains only bounded compact feedback. | In isolated replay, freeze the input hypothesis and profile, then remove one applied entry at a time. Compare with an independently supported correction and wrong-context negatives. This isolates matcher behavior, not acoustic decoding. Ambiguous edits or changed intention must remain unattributed. A durable joined outcome record would need a storage/data-flow proposal. |
| Does a fix prevent the same mistake from returning? | The stress suite records repeated policy regressions; real-audio evaluation retains the `cost` → `costs` mistake. | Use the already-prioritized bank of observed failures alongside fresh validation. Keep adverse contexts, correlated retries and stale-feedback cases. Hidden audit labels never enter that bank; compare every candidate with strong fixed policies on fresh future episodes. |
| Does learning delay dictation? | Desktop diagnostics expose transcription, cleanup and save durations; replay measures learning components separately. Existing workers await observation/feedback transactions. | Compare matched learning-active and frozen-memory experimental runs, preserving quality checks. Attribute queue wait, profile read, matcher and SQLite time before measuring native stop-to-final/insert and sustained resource interference. The frozen comparator is a test control, not a returning product opt-in. |
| Can successful changes be reused across models? | Application-owned memory is independent of model identity; the offline controller has six typed policy choices. | Version tested policy recipes with their applicable context, supporting failures and rejection cases. Revalidate after a model change. Do not interpret a passing recipe as permission to rewrite arbitrary application code on the user's device. |

The requested **offline failure-bank comparison is complete**: on 97 fresh-seed histories, held-out word edits increased from **2,599 current → 2,625 failure bank**, while the previously identified fixed context control scored **1,464**. The bank blocked ten rollbacks, including useful adaptation, and showed no gain on 304 cached Svarah outputs. The [full comparison](../benchmarks/asr/2026-09-18-failure-bank-comparison.md) records mixed all-episode/final-only results, repeated timing and validation. This variant is not qualified for live use. It introduces no GLM dependency or model call. Richer live attribution, scheduling and policy activation still need concrete proposals and qualification; retain the [current storage limits and collection-off contract](personalization/storage-and-privacy.md).

A subsequent [scoped-policy refinement](../benchmarks/asr/2026-09-18-scoped-policy-comparison.md) tests a stronger fixed fallback plus context-specific updates on another fresh seed range. Held-out edits are **2,598 original adaptive → 1,372 scoped**, versus **1,468 fixed context** and **1,412 global adaptive with the same initialization**. Most gain comes from initialization; scoping adds a smaller benefit in support shifts. This is a positive authored-simulation result with remaining per-case regressions and no cached public-audio gain. It does not demonstrate semantic intent, accent adaptation, live RSI or deployment readiness.

**Implementation follow-up, 19 September:** the user separately approved the fixed teaching-context guard for desktop automatic vocabulary. It now captures bounded terms from independent edits and filters cleanup vocabulary/final replacement from the same raw-hypothesis snapshot. [Application qualification](personalization/evaluation.md#integrated-teaching-context-guard-19-september-2026) records 127 core/data/desktop tests, 45 browser scenarios, native checks and a 64-case mechanism comparison that retains eight paraphrase regressions. The adaptive controller remains offline; this fixed rule can accumulate user-specific context without learning a new algorithm.

The transfer proposed here is **category 1: frozen-weight application evaluation**. Kernel precision changes, fusion and communication scheduling belong to **category 2: native runtime internals**, and require evidence for our exact runtime/backend before consideration. **Category 3: checkpoint training** remains separate. No performance number from this post qualifies an ASR checkpoint, changes an inference default or establishes a latency budget for background learning.

## Prioritized application experiments

These are **remaining engineering proposals**, informed by the completed isolated comparison; they are not promises of improvement. Existing automatic spelling learning remains core product behavior.

1. **Qualify context-specific adaptation beyond simple lexical simulations.** The first global bank failed; the scoped fallback/controller alternative now improves the fresh simulation above. Test real longitudinal feedback, paraphrases, ambiguous scope and changing preferences before proposing live integration. Keep the same-start global and fixed controls, historical labels out of fresh improvement counts, and audit/test references unavailable. The current positive result does not justify broader policy search or retuning on its held-out answers.
2. **Attribute outcomes to particular memories.** Distinguish a term being retrieved, a term actually changing text, and a later user correction undoing that change. An edit touching several stages may not identify the cause; retain uncertainty. Evaluate case-local negative evidence before changing a global rule. Do not relabel unchanged text or Copy as endorsement. This would extend the existing evidence model and requires a concrete storage/data-flow proposal.
3. **Adapt context retrieval separately from spelling truth.** Start with small, typed project/language/context cues and the existing lexical selector. Test the same word in unrelated contexts, including the observed `cost`/`costs` failure. Keep original correction provenance immutable. Do not introduce a graph database, embedding model or external search service solely because a paper uses a graph or index.
4. **Consolidate memory conservatively.** Test merging duplicate aliases, reducing the rank of poorly supported entries and retiring harmful context associations. A rarely used name is not necessarily wrong; non-use must not erase an explicit preference. Preserve independent support, undo, forget epochs and protected words through every transformation.
5. **Qualify a live policy loop only after the offline comparison succeeds.** A future background integration should use bounded typed policy changes, a fixed independent evaluator, versioned candidates, atomic activation and rollback, and cancellation when dictation needs resources. Those scheduling/persistence properties are not implemented by naming the feature RSI. The concrete integration proposal and approval belong in #34 under the project's architecture rule.

The negative bank result and limited positive scoped result keep broader qualification ahead of expanding the optimizer's authority. Semantic intent and repair interpretation still follow the separate [phase-B proposal](personalization/roadmap.md#b-semantic-personalization-with-frozen-weights). These mechanisms can fit automatic product behavior without requiring users to tune thresholds or maintain dictionaries.

## Acceptance evidence for any next experiment

Freeze development, fresh validation and later audit partitions by user/session/source/repair chain. Preserve unedited examples, wrong-context negatives, sparse/misleading feedback, changed preferences, model changes and multilingual cases. Simulated feedback must be explicitly labelled. Synthetic utterances cannot supply independent evidence of a real user's intention.

Evaluate the incumbent and strong fixed controls under the same context and resource budget. Report all outputs, rejected candidates, failures, harmful changes and reversions. Keep the scorer and acceptance thresholds fixed while optimizing; repeated candidate search against one validation set can overfit. A fresh final set and repeated-round testing are required even when historical replay improves.

Measure later correction actions/editing time, scoped memory precision/coverage, protected-meaning failures, and benefit sustained over successive sessions. Separately measure feedback-to-memory-ready time, idle-work CPU/RAM/energy and interference with first partial, stop-to-final and insertion. No lab headline speedup or current spelling-stage microbenchmark establishes this future controller's latency.

This survey proposes category-1 frozen-weight application experiments. It proposes no category-2 runtime-internal decoder/kernel work. Category-3 training in some papers remains separate from the user's current local, model-independent learning requirement. Existing model/runtime pins and artifact-qualified results remain in [ADR-0016](adrs/0016-automatic-local-spelling-learning.md#evidence-and-inference-boundary); this review changes none of them.
