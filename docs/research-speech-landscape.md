# Speech model landscape for the Rust application

Current selection update (15 September 2026): [#37](https://github.com/rahulsharmavishwakarma/transcribe/issues/37) makes Cohere Transcribe plus Qwen writing cleanup the user-selected default. The earlier default/integration status below is historical; consult [application internals](internals.md) for current capabilities.

Research checked **14 September 2026** against publishers’ documentation, repositories and model cards. Cohere is now the fresh-settings default. Nemotron is integrated as the selectable multilingual/live adapter, Qwen3-ASR and Cohere as completed-audio sherpa-onnx adapters, and LFM2.5 Audio as an English completed-audio llama.cpp/mtmd adapter. Kyutai's former application adapter was removed after a local screen failed its declared quality and real-time gates; its research entry remains historical evidence. Other models in the table remain candidates until an architecture-specific adapter is implemented. Consult the [language and recommendation matrix](language-support-and-recommendations.md) for current local evidence.

Historical candidate ordering from 14 September, before the local Whisper screen: keep the existing NVIDIA path and add **Whisper through whisper.cpp as the broad-language native baseline**. Evaluate **Moonshine Streaming for lightweight English dictation**, **Cohere Transcribe for its supported languages**, and **Microsoft VibeVoice-ASR-BitNet for CPU efficiency**. Microsoft’s larger ASR models suit meeting transcription and speaker attribution more than a small default desktop download. This ordering is an engineering recommendation based on the deployment requirements below, rather than a claim that one model wins every accuracy benchmark.

The [18 September Whisper investigation](research-whisper.md) supersedes the earlier Whisper integration ordering with checkpoint-specific evidence, native decoder constraints, and a concrete proposal. Whisper remains outside the production model registry.

## Microsoft products that should not be confused

**VibeVoice-Realtime-0.5B is text-to-speech**, whereas VibeVoice-ASR and VibeVoice-ASR-Streaming recognize speech. The shared family name does not make their weights interchangeable. [Microsoft repository](https://github.com/microsoft/VibeVoice)

**Phi-4-multimodal-instruct** accepts text, images and audio and can perform transcription, translation, speech question answering and summarization. Its card lists eight audio languages—English, Chinese, German, French, Italian, Japanese, Spanish and Portuguese—without Hindi, and declares MIT licensing. This is an optional audio-understanding experiment, not a tiny replacement for the separate ASR and cleanup stages. Its modality-specific processing must be retained; a text-only GGUF import is insufficient. [Phi model card](https://huggingface.co/microsoft/Phi-4-multimodal-instruct)

**Azure Speech** is a separately provisioned service. Microsoft’s language table includes `hi-IN` and distinguishes real-time, fast, batch and refinement capabilities. It is a plausible cloud Hindi baseline, but service availability is not downloadable model availability. A cloud adapter would need explicit user selection and credentials. [Azure language support](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/language-support?tabs=stt)

## OpenAI: local Whisper and hosted transcription are separate options

For local inference, Whisper’s official Python implementation is a reference; **whisper.cpp provides the native execution path**. It exposes a C interface suitable for a Rust FFI wrapper, CPU inference, integer quantization, Metal, CUDA, Vulkan and other backend options. Core ML can accelerate the encoder on Apple’s Neural Engine; OpenVINO targets supported Intel hardware. Conversion may require Python during packaging without requiring Python in the shipped desktop runtime. The microphone example repeatedly transcribes windows; it should be described as an incremental wrapper around Whisper rather than a native streaming transducer. [whisper.cpp implementation and examples](https://github.com/ggml-org/whisper.cpp)

Current OpenAI documentation recommends **`gpt-transcribe` for file transcription** and **`gpt-live-transcribe` for live audio**. Existing `gpt-4o-transcribe` and `gpt-4o-mini-transcribe` integrations remain documented. `gpt-4o-transcribe-diarize` adds speaker labeling; `whisper-1` remains relevant to specific timestamp, subtitle and translation workflows. Streaming partial text from an uploaded completed file is different from sending ongoing microphone audio. These are hosted API paths, not local Whisper checkpoints or downloadable tiny models. [File transcription guide](https://developers.openai.com/api/docs/guides/speech-to-text), [GPT-Transcribe](https://developers.openai.com/api/docs/models/gpt-transcribe), [GPT-Live-Transcribe](https://developers.openai.com/api/docs/models/gpt-live-transcribe)

For this application, hosted models are optional comparison or fallback providers. They require an intentional upload path; selecting a local model must continue to keep inference local. This report does not recommend replacing the Rust backend with a Python API client.

## CPU, GPU and memory: what the evidence supports

Published throughput is not end-of-utterance latency. VibeVoice-ASR-BitNet reports **RTF 0.77 with three threads**, but the stated setup is an **AMD EPYC 7V13 with 20-second audio**. Its reported speed advantage over Whisper.cpp is useful motivation to test, not an established result for an M5 laptop, phone or our complete ASR → cleanup pipeline. The 1.579 GiB figure describes model files, not measured peak process memory. [BitNet benchmark conditions](https://huggingface.co/microsoft/VibeVoice-ASR-BitNet)

Whisper’s official VRAM estimates—roughly 1 GB for tiny/base through 10 GB for large, with 6 GB for turbo—refer to its published implementation. Its relative speed table uses an A100. Neither table predicts quantized whisper.cpp RAM or latency on a CPU. [Whisper model table](https://github.com/openai/whisper)

Recommended local experiment order:

1. **Apple Silicon:** retain the working NVIDIA-export baseline; compare whisper.cpp Metal with CPU on identical recordings, then evaluate Core ML encoder conversion if measured latency or energy warrants the extra artifact.
2. **Windows/Linux CPU:** compare quantized Whisper, Moonshine’s native streaming library and VibeASR.cpp. Record actual AVX/NEON capabilities and thread count.
3. **NVIDIA GPU:** benchmark dedicated ASR models with batch size one for interactive use. Separately measure larger batches for archive processing; a serving throughput result should not set the UI latency promise.
4. **Mobile and smaller devices:** start with the smallest supported English model when English is sufficient. Validate memory pressure and sustained battery/thermal behavior before attempting larger multilingual models.

These are evaluation proposals, not hardware compatibility results for the current build. For every run record cold load, first partial result, final result after stop, cleanup time, peak RAM/VRAM, energy where measurable, and real-time factor. Keep decoding settings and audio segmentation fixed for comparisons. Benchmark Hindi, English and mixed Hindi-English separately, including names, numbers, negation, pauses, background speech and silence.

## Tiny cleanup remains a separate decision

Retain **Qwen3.5-0.8B** as the current small baseline; its official checkpoint declares Apache-2.0. Use a supported text-capable export and the correct chat template, and compare quantization on preservation accuracy rather than assuming the smallest file is best. This is a recommendation to evaluate the existing implementation, not a claim that the model reliably reconstructs unspoken intent. [Qwen checkpoint](https://huggingface.co/Qwen/Qwen3.5-0.8B)

Cohere’s **Command and Aya** families should be considered separately from Cohere Transcribe. **Tiny Aya Global** is a 3.35B multilingual text-generation candidate covering Hindi, but is several times larger than the current cleanup baseline. Its card declares **CC-BY-NC-4.0 plus Cohere’s acceptable-use terms**; commercial use requires a separate arrangement. Hindi-capable text generation cannot repair the absence of Hindi acoustic recognition upstream. [Tiny Aya Global](https://huggingface.co/CohereLabs/tiny-aya-global), [Cohere model catalog](https://docs.cohere.com/docs/models)

For punctuation and capitalization, first test a constrained formatter or task-specific punctuation model against a general LLM. Keep the raw transcript, make rewriting optional, and evaluate preservation of names, numbers, negation and meaning. Store user-reviewed corrections separately from model output. Automatically training on unreviewed “cleaned” text would reinforce both recognition and rewriting mistakes.

## Consequence for Hugging Face plug-in support

The current profile importer supports a specific sherpa-onnx NeMo transducer bundle and a single supported llama.cpp cleanup GGUF; built-in Nemotron uses a separate pinned NeMo-Speech.cpp adapter. This does **not** make every model above immediately usable. Cohere and Qwen3-ASR now have compiled completed-audio adapters. Liquid LFM2.5 Audio now has a compiled English CPU adapter through the pinned llama.cpp/mtmd frontend. Voxtral also requires architecture-specific integration; Whisper needs Whisper preprocessing/decoding; VibeVoice needs audio tokenizers; BitNet ships two specialized artifacts; Moonshine has a dedicated streaming runtime.

Represent compatibility as an adapter capability: architecture, audio frontend, required files, quantization, languages, partial/final result behavior, timestamps, speaker labels, hardware backend, license and revision. Keep the common Rust interface stable while adding tested adapters. Never infer “works on CPU,” “supports Hindi” or “supports streaming” merely from a Hugging Face task label or file extension.
